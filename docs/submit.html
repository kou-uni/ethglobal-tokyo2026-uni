Description

3627 chars · min 280 
Scraping the open web is free and contaminated. An agent cannot tell what a human wrote, because synthetic text is free, abundant and indistinguishable at scale. So the scarce thing is no longer information — it is an answer only a person who lived it can give truthfully. A model can invent an answer to "what made you put it back on the shelf." It cannot invent a true one.

That is a market, and it has a problem: the buyer never sleeps and the seller does. Open a counter in the agent economy and some fifty requests arrive overnight. Answer them all by hand and it does not scale; approve them all automatically and you have lost control of your own data.

Yohaku is the layer in between. Ten ordered rules decide every incoming request — first match wins — into auto, human or deny. What reaches the person is bundled, ranked and held to a daily cap she sets. We generate a night, run it through the real router twenty times, and the arrivals wander between 46 and 54 while the number reaching her is 2 in every single run. That sentence is the output of npm run verify, not a claim.

Three properties are the product:

1. Everything fails to deny. Engine down, screening unreachable, identity check failed,
deadline passed with no answer — all of them refuse. Silence is not consent.

2. The guarantee lives in the schema. A model is consulted on exactly one rule, and the
values it can return are 'ask' and 'drop'. There is no value meaning "pass". A prompt
injection that fully convinces the model still cannot widen access, because widening is
not expressible.

3. A refusal you cannot inspect is the same as never having been asked. Agents really do
ask for a home address and for a wallet. Those requests are in the demo, refused under a
rule the owner set, and she can open /dropped and see what each one wanted with the rule
that stopped it named beside it.

We did not invent a protocol for the arriving side. Requests reach Yohaku over A2A, whose v1.0 specification moved to the Linux Foundation, and payment rides the x402 transport that A2A already defines — the agent is told payment is required through the task state the specification provides, rather than through anything of ours. Discovery is an Agent Card at a well-known path. That matters for the shape of the market: many agent-facing directories can exist, and a person still needs exactly one router in front of their own attention.

In the language of Google's AP2, Yohaku is a Trusted Surface: the non-agentic surface that obtains informed human consent before a mandate is signed. AP2 puts a MUST on exactly that role, because "the Agent itself is a potential attacker". We had already built it that way.

What none of the existing protocols cover: AP2, UCP and ACP all assume the counterparty is a merchant. MCP's elicitation — the one standard place an agent asks a human for something — explicitly forbids requesting personal data. And nobody has defined how many times a day an agent economy may interrupt one person. That last number is what Yohaku holds.

How it stays alive: Yohaku charges for a decision, never a share of what the seller earns. One atomic unit per request routed, offered as an optional extension on the payment the buyer was already making, and the seller's proceeds never enter that ledger at all. The accounting is deliberately built so it cannot report collected money — the summary field is typed as broadcast: false — because a router that could quietly take custody is a router you would be right not to install.

MIT licensed, because a surface that decides what a person never sees has to be one they can read.

How it's made

5062 chars · min 280 
TypeScript, no framework. src/core is pure — the router takes a request, a policy and a clock and returns a verdict; no I/O, so the same code runs in the tests, in the server and in a single-file console that opens from a USB stick with no network.

Ports and adapters: ClassifierPort, IdentityPort, ScreeningPort, PermissionsPort, SettlementPort. The guarantee is in the port's schema, not in the adapter, so swapping an implementation cannot weaken it.

The public demo is /experience: an agent workspace and a mobile human inbox. Fifty generated requests go through the real routing core, with configured Intercepta screening and bounded Jev decision support. Before authentication, a one-use, two-minute handoff moves the run to a phone. The original desktop becomes a read-only observer of paid answers; it cannot see the phone's proof or drafts.

World ID in this demo uses production IDKit, not the legacy OIDC sandbox. The backend verifies the proof and binds its signal to the browser, run, recipient, policy and quoted payments. Access lasts fifteen minutes. The user opens World App and returns to the original phone browser. Authentication alone is not a transfer: the explicit inbox action then collects one delegated sample reward, and a separate answer-and-consent action triggers the human-answer reward. World establishes the required personhood credential; it does not establish wallet ownership or the truth of an answer.

The older World OIDC adapter remains a separate path. Its PKCE and sandbox auth_time/amr findings are documented as earlier experiments, not as the authentication mechanism of the public mobile demo.

x402 (protocol v2, Base Sepolia). The published x402 npm package still speaks v1 (X-PAYMENT); the deployed facilitator answers x402Version 2 (PAYMENT-SIGNATURE). We build on @x402/core, whose only dependency is zod, and accept both header names. The server confirms at startup that the facilitator actually supports the configured scheme and network.

In the ordinary request path, an EIP-3009 authorization is kept separate from settlement and expires at the request deadline. The public /experience demo uses the same x402 adapter but creates its authorization after the required consent and a fresh payer screening. A pending or refused request is not counted as paid, uncertain settlement is not retried automatically, and an answer reaches the demo buyer only after settlement succeeds.

The public mobile run is now backed by two independently checked Base Sepolia transfers: 0x8b60210db922288cfd3f4a792c221ba28863ad7b929972e47d6145468315da2d (120 atomic test USDC for the delegated sample) and 0xb652ed83b10b2faf50b2859b224dd041b00f0903a78e6a84b6c949daab2659d6 (1,001 atomic for the human answer). The desktop changed to observer mode after phone handoff and received both paid answers. RPC receipts confirmed the configured token, direct buyer-to-recipient transfers, exact amounts and success; BaseScan showed both transfers too. The total is 0.001121 test USDC. These are new /experience receipts, distinct from the earlier /try evidence. The verification record is docs/build/evidence/experience-public-payment.json; it contains no raw World proof or personal answer text.

ENSv2 (Ethereum Sepolia — a different chain from the settlement, which costs an hour if you confuse them). A name is registered and resolved through a permissioned resolver: yohaku-minta-2026.eth, receipt 0x8e13e0ad…, resolver a proxy of PermissionedResolverImpl, paid 8.000021 MockUSDC for 365 days. Role bits confirmed from the chain via decodeSetter — all five text keys at role 16 — after direct eth_call to the implementation reverted for every selector.

The delegate boundary runs on chain, not against a mock. A delegated account was granted the setter role for yh:proposal only; it wrote yh:proposal and succeeded (0x16873dfa…), wrote yh:policy and reverted with EACUnauthorizedAccountRoles (0xb459618b…), and after the owner revoked, the proposal write reverted too (0x2380d0fe…). Six receipts, in order, on Ethereum Sepolia. Simulating the same write today still reverts with the same error, so it is not a historical artefact — the contract refuses it right now.

Anti-guessing is enforced rather than remembered. npm run verify re-derives every number in the documents by running the code, and refuses any hardcoded model id, API endpoint or contract address in src/ or scripts/. It also fails if any published page quotes a test or claim count the test run did not produce. We added that last check today and it immediately found seventeen stale counts, three of them on our own published site. It then caught its own author: adding an eleventh claim made the count in eight other files wrong, and the check failed until those were fixed too. The claims are published as machine-readable JSON, because the reviewer we are most likely to get is an agent.

409 tests. 12 verified claims. Two numbers in these documents were measured, found false, and withdrawn in place — the retraction is still visible in ASSUMPTIONS.md.

How AI tools were used

1302 chars 
Claude Code wrote most of this repository, with the two of us reviewing and deciding. It was also used for something less obvious: after we found three numbers in our own documents that had been true when written and false by the time anyone read them, we had it build the checks that now fail the build on that — npm run verify re-derives every quoted figure by running the code, refuses any hardcoded model id, endpoint or contract address, and rejects any document quoting a test or claim count the run did not produce. Those checks have since caught their own author several times.

Inside the product, three models are called for real rather than mocked. Jev, a decision model from TypeSafe AI, is consulted on rule 9 — the one case no rule settled — and Claude and GPT sit behind the same port as alternates. We ran the same request through Claude and GPT and they disagreed, which is the point: the guarantee cannot depend on having picked a good model.

So the model is deliberately boxed. It is asked one typed question whose only options are ask and drop. There is no value meaning pass, so a request that talks a model into approving it still cannot be approved — we measured that with a prompt injection, which moved the verdict from ask 0.99 to drop 0.89 and could not move it any further.

ENS — Best Use of ENSv2 — How are you using this API?

827 chars 
You can delegate to an AI without letting the AI rewrite what it is allowed to do. The owner's policy lives under text keys on a permissioned ENSv2 resolver, and a delegated agent holds the setter role for exactly one key — it can propose, and it cannot widen its own authority. That boundary is rule 0 of our router, and it is the contract that refuses the write, not our server. Six transactions on Ethereum Sepolia show it: a proposal that succeeded, a policy write that reverted with EACUnauthorizedAccountRoles, and a proposal that reverted after revocation. Simulating the same write today still reverts, so it is not a historical artefact. The Ethereum Sepolia delegation demonstration is separate from the public mobile /experience payment journey; we present both rather than claiming that the mobile flow invokes ENS.

ENS — Best Use of ENSv2 — Additional feedback

927 chars 
It works, and getting there cost more than it should have.

The published SDK's authorizeTextRoles and the deployed contract's grantSetterRoles are different APIs, and neither the mismatch nor which package version can write is reachable from the documentation — only @ensdomains/ensjs@5.0.0-sepolia-fix.1 writes at all; latest has no v2 and alpha is read-only. We lost hours to that before finding the fix branch.

Reading the role bits was the other one. eth_call against the implementation reverts for every selector, so decodeSetter was the only way to confirm what we had granted.

The one line of documentation that would have saved the most: the per-key grant carries the role implicitly and takes no bitmap.

What we would not claim, and would ask you not to let teams claim: revocation is not new to v2. The thing that is genuinely v2 is the delegation boundary, and it is a better story than the one people reach for.

Curvegrid — Best AI Agent Project — How are you using this API?

600 chars 
An agent that works around the clock spends around the clock, and the question that decides whether a team can live with that is not how much — it is which movements a person has to see at all. We built that half-step: ten ordered rules run before any payment, and only a request that came out as auto settles without a person. The agent never signs on the owner's behalf, and the owner's constraints are read from a permissioned ENSv2 resolver rather than from our database. Intercepta — Safe Agent-to-Agent Payments with x402 — How are you using this API?

594 chars 
Rule 4 is the only refusal in our router that is not about permission: the grant is valid, the category is allowed, the amount is fine, and the payment still does not go because of where the money would come from. A live Quick Scan runs on the declared payment source before we settle or deliver, and its result decides the branch — clean settles, flagged refuses in your own words, and unavailable refuses too, because if we cannot check we do not move money. Intercepta — Safe Agent-to-Agent Payments with x402 — Additional feedback

1166 chars 
Fast to integrate — we went from key to a live branch in an afternoon. Three things we found that you may want to know.

The auth header is not in the material we had. x-api-key works; authorization: Bearer, apikey and api-key all return 403 with the same message as no header at all. We found it by trying six.

The endpoint is account-scoped, and that surprises you in the worst direction. A sanctioned *contract* — 0x722122dF12D4e14e13Ac3b6895a86e84145b6967, on OFAC's list — answers 404 with "An Externally Owned Account with this address doesn't exist". That is the response that most looks like "nothing wrong here". We map 404 to unavailable, which refuses.

And one worth checking on your side: 0x8589427373D6D84E98730D7795D8f6f8731FDA16, also OFAC-listed, comes back toxicScore 0 on both quick-scan and toxic-score. We are not treating your API as a sanctions oracle because of it, and we would suggest you do not let integrators treat it as one either.

The best part of the API is the one we did not expect: every trait carries a human-readable description, so the sentence we show the person whose payment stopped is yours and not an accusation we wrote.
