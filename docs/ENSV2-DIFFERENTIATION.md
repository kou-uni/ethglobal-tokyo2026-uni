# ENSv2の公式の推しどころ — Norenで何を実演するか

調査日：2026-09-25

**公式資料から一つに要約するなら、ENSv2の中心は「各名前の下に、自分のルールで管理できる名前空間を持てること」。Norenでその価値を最も明確に示せそうなのは、EACとPermissioned Resolverによる、エージェントへの細かい権限委任である。**

「取消可能な許諾証」だけではENSv2の差分が弱い。**「エージェントには提案の更新だけを許し、本人の許諾条件や送金先は変更させない。その境界をENSv2のコントラクトが強制する」**を第一の実演候補にする。

この順位は公式概要・仕様・今回の賞要件からの分析であり、ENSが「この機能が審査の1位」と公表したものではない。実装・疎通は未実施。

## 1. ブースの反応をどう受け止めるか

ユーザーから、「剥奪できる部分がよい」と説明したところ、ENSブースで「それは前もできた」という趣旨の返答があったとの共有があった。

**この指摘は従来版の仕様と整合する。** Name Wrapperの公式資料は、親による子名の置換・削除と、それをできなくする `PARENT_CANNOT_CONTROL` fuseを説明している。[S5]

したがって、取消という機能の存在そのものをENSv2の新規性として売り込むのは弱い。ただし、名前一つの取消と、v2の階層構造による部分木の差し替えは区別する必要がある。

話した方の氏名・役職は確認していない。特定個人の公式見解や、全審査員の評価としては扱わない。本書の根拠は公開一次資料とする。

## 2. 「公式の一番」をどう読むか

公式概要はENSv2の目的を、スケーラビリティ、モジュール性、将来の拡張性として説明し、主な変更に次を挙げる。[S1]

| 公式の変更点 | 何が変わるか | Norenとの関係 |
|---|---|---|
| **Hierarchical Registries** | 単一のフラットなレジストリから、子レジストリをつなぐ階層構造へ | 名前空間ごとに管理・委任・更新の境界を作れる |
| **Permissions as Standard / EAC** | Name Wrapperの権限制御を、プロトコルの共通ロール管理として組み込む | 本人・代理エージェント・運用者の役割を分ける材料 |
| **Per-Account Permissioned Resolvers** | アカウントごとのリゾルバ、細かいレコード権限、レコード共有 | AIに許す更新と本人だけが行う更新を分離できる |
| Grace Periodの短縮 | 更新猶予期間を90日から28日へ | 今回の中心的なデモにはしない |

**アーキテクチャ全体の中心は階層レジストリ。その上でNorenが使うべき具体機能は、EAC＋Permissioned Resolver。**

「ENSとして嬉しい」の根拠は、今回の賞ページが、レコードを限定した権限委任を例示し、AIエージェントに名前空間・アイデンティティ・権限を与える応用を歓迎していること。単に名前を表示する用途ではなく、ENSv2の機能が製品の中心であることを要求している。[S2]

## 3. 従来からできたことと、v2の差分

| 話題 | 従来からあるもの | v2で示すべき差分 |
|---|---|---|
| サブネーム | v1にも存在し、名前自体は階層的 | **保存・解決・管理の実装が階層レジストリになる**。v1に階層名がなかったと言わない |
| 取消・譲渡制限・期限 | 親の制御、Name Wrapperのfuse・expiry | 共通のロール管理、管理権限を保持する範囲での付与・取消、サブツリーの操作 |
| 管理の委任 | 従来の権限・承認や独自コントラクトでも可能 | **標準のRegistryとResolverで細かい権限の分離を組み合わせられる** |
| エージェントにENS名を付ける | 名前・text recordを利用すれば従来でも可能 | エージェントが実際に何を更新できるかをEACで強制する |
| 許諾の公開参照 | 従来のtext record等でも構成可能 | v2の権限分離や共有レコードと組み合わせ、更新者の権限まで示す |

根拠：v1 Name Wrapper、v1 Public Resolver、v2概要・EAC・Resolver仕様。[S1][S3][S4][S5][S8]

「以前は一切委任できなかった」「ENSv2だけが取消可能」は言わない。比較するのは、**標準機能としての構成、権限の粒度、管理方法**。

### 混同しやすい3種類の「取消」

1. **名前の取消**：子名を登録解除・置換すること。従来版でも可能な構成がある。
2. **ロールの取消**：あるアカウントから、特定の操作権限を外すこと。EACでは、管理権限を保持する範囲で再付与も可能。[S3]
3. **階層の切り替え**：親から参照する子レジストリを差し替え、名前空間全体の解決先を変更すること。v2の階層モデルが直接扱う。[S6]

ただし、EACの全操作が無条件に可逆ではない。管理権限を全員が放棄した場合やRegistry固有の制限があり、標準Permissioned Registryでは個別名のadmin role付与が登録時に制限されている。[S3][S7]

## 4. Norenでの推奨順位

順位は今回の製品・実装ゼロという状況に対する提案。

| 優先 | 活用 | 価値 | 判断 |
|---|---|---|---|
| **A：最優先** | **EAC＋Permissioned Resolverで、エージェントの書込権限を限定** | AIへ委任しても、AIが自分に都合よく本人の許諾を書き換えられない | 小さく実動検証する |
| **B：次点** | 名前空間ごとに子レジストリを管理し、委任・差し替えを示す | 権限の管理単位が名前の構造として見える | A成功後、余裕があれば |
| C | Record linkingで、複数名が同じ設定を参照 | 同じ設定のコピーを減らせる | 今回は後回し |
| D | Namespace aliasingで名前空間を別名から参照 | ブランド変更・移行などの応用 | 今回は後回し |
| E | エージェントの接続先をENSから発見 | 「誰に、どこから依頼するか」を名前から引ける | 補助機能。v2固有の主張にしない |

**機能を全部盛ることは推奨しない。AをNorenの実際の動作に接続できれば、取消だけのデモよりv2の意義を説明しやすい。** 受賞の保証ではない。

## 5. 第一候補のデモ：提案できるが、自分で許諾を広げられない

### 役割

Norenの顧客は引き続き買い手エージェント。以下の「代理エージェント」は、**売り手Aliceの依頼整理を補助するエージェント**であり、顧客とは区別する。

| 主体 | 許す操作の案 | 許さない操作の案 |
|---|---|---|
| Alice本人の管理アカウント | 許諾ポリシーの更新、代理への権限付与・取消 | — |
| Aliceの代理エージェント | 依頼を整理した提案の参照・ハッシュを更新 | 許諾条件、受取先、他者への権限付与、リゾルバの変更 |
| Norenルーター | 本人の許諾と提案を読み、独立に検証して処理 | AIの提案だけを根拠に本人の許諾範囲を広げる |

説明用のキー例は `noren.proposal` と `noren.policy`。これは独自のアプリ用キーであり、ENSの標準キーではない。公開するのは最小限の状態・参照・ハッシュとし、申請内容や個人情報の本文を載せない。

### 実演の一周

1. Aliceが、自分の許諾状態と受取先を設定する。
2. 代理エージェントに、**提案キーだけ**の書込権限を与える。
3. エージェントが提案を更新する。**成功する。**
4. 同じエージェントが、本人の許諾キーや受取先を書き換えようとする。**アプリのボタン制限ではなく、コントラクトの権限検査で失敗する。**
5. 正規の許諾を読んだNorenが依頼を処理する。提案があっても許諾外なら通さない。
6. Aliceが提案キーの権限を取り消す。同じエージェントの提案更新が失敗する。

4と6の検証はスクリプトやウォレットからの直接呼び出しでも行う。AIが実際に危険な判断をしたかのような演出ではなく、**権限境界のテストであることを示す**。

停止の理由は分けて見せる。

- **ENSv2が止めるもの**：権限のないレコード更新。
- **Norenが止めるもの**：有効な許諾のない情報提供・決済。

EACはAIの提案内容が正しいことを保証しない。また、書込権限を取り消しても、既に書いた提案が自動で消えるわけではない。過去の提案を受け付ける条件・期限はNoren側で確認する。

### ブースで伝える一文

> 「取消可能な名前を作るだけではなく、ENSv2のEACとPermissioned Resolverで、売り手の代理エージェントには提案レコードだけを更新させます。本人の許諾条件や受取先は変更できず、直接コントラクトを呼んでも失敗するところを見せたいです。」

英語版：

> “We want to use ENSv2's EAC and Permissioned Resolver to let a seller's agent update proposals, but never rewrite the seller's consent or payment destination. We'll demonstrate successful authorized writes and rejected unauthorized writes, then connect that boundary to Noren's routing.”

実装前は「作った」ではなく「作りたい」と伝える。実装後に実物へ合わせて直す。

## 6. 実装で最も注意する仕様

### 6-1. Resolverの権限は「名前ごと」ではない

**現行のPermissioned Resolver公式資料は、レコードキー等の権限が、そのリゾルバインスタンスで提供する全名に及ぶと明記している。** `alice`名を引数にしたから、その名前だけの権限になるわけではない。[S4]

例えば `description` の更新を許すと、同じインスタンス内の他の名前の `description` にも書ける。**独立した売り手を、同じリゾルバへ無条件にまとめない。**

標準のアカウントごとの分離を基本にし、同一アカウント内でも名前ごとに別の境界が必要なら、インスタンス分離や別設計が必要か確認する。Registryの名前単位の権限と、Resolverのキー単位の権限を混同しない。

### 6-2. キー限定の付与は `grantSetterRoles`

現行資料では、Permissioned Resolverの汎用 `grantRoles` は無効で、キー等に限定する場合は `grantSetterRoles(setter, account)` を使う。名前・値部分は権限のスコープには使われず、setterの種類と対象キー等から権限を決める。[S4]

古いサンプルを見て、Registry用の付与手順をそのままResolverへ流用しない。実装前に現行ABIとデプロイを確認する。

### 6-3. 広い権限が残ると、限定・取消の実演が成立しない

対象キーの権限を取り消しても、同じ操作のroot権限があれば書込が通り得る。admin・upgrade・link権限や、リゾルバ／子レジストリを変える権限など、間接的な回避経路も確認する。[S3][S4][S7]

本人とエージェントは別の署名主体で検証する。サーバが常に本人の広い権限で代わりに署名しているだけでは、「エージェントの権限がENSv2で制限されている」証明にならない。

EACのroot権限は**そのコントラクト内**での権限。名前に `ROOT_RESOURCE` を使えば別のRegistry・Resolverまで一括制御できるという意味ではない。[S3]

### 6-4. Record linkingは、キー単位の継承ではない

複数名を同じレコード束へリンクすると、書換えはその束を使う全名へ反映される。公式仕様上は**束単位の共有**で、任意の一つのキーだけを親から継承する機能ではない。デフォルトへのフォールバックも名前単位である。[S4]

「テンプレートは共有するが、本人の許諾・送金先だけ独立」としたい場合、その分離を別途設計する必要がある。今回、単に加点のために追加しない。

### 6-5. サブツリーの切替は、既存コントラクトの消去ではない

公式は、子レジストリの差し替えにより、名前空間の下位全体を一操作で切り替えられると説明している。[S6]

ただし旧レジストリのコントラクトやデータが消えるわけではない。旧アドレスへの直接アクセス、古いキャッシュ、他名からのaliasをどう扱うかは別問題。Norenは正規の名前解決経路・最新状態に基づいて実行を許可する必要がある。

## 8. ブースで確認する質問

次は感想ではなく、具体的な技術仮説として確認する。

1. **「提案キーだけ委任し、許諾条件と受取先の変更はコントラクトで拒否する実演は、今回のENSv2賞で見たい利用例に合っていますか？」**
2. 「Permissioned Resolverの権限は同じインスタンスの全名に及ぶ理解です。売り手ごとのインスタンス分離が、この用途の標準的な構成ですか？」
3. 「`grantSetterRoles`でキー限定の書込を付与・取消する、現行Sepolia向けの最短サンプルはありますか？」
4. 「Registry階層の実演も足すなら、独立した名前空間の委任と、サブツリー切替のどちらがこの用途に適していますか？」

担当者の回答は、その場の助言として記録する。賞の保証と解釈しない。本調査ではブースや本人への連絡は行っていない。

## 9. ENS／Intercepta比較への変更

前の比較では「発行→参照→取消→拒否」をENS採用の検証条件とした。これは疎通確認としては有効だが、**ENSv2固有の価値を示す受賞戦略としては不足し得る**。

今後は、次の成立までをENSの技術検証条件にする。

- エージェントの限定された更新が成功する。
- 同じエージェントの許諾・受取先の更新が、ENSv2側で拒否される。
- 本人による権限取消後に、元の限定更新も拒否される。
- その状態をNorenの実際の処理へ接続する方法が明確である。

時間の上限を増やすための追加ではなく、**試す対象を「取消だけ」から「権限分離」に変更する**。実装ゼロからこれが通らない場合は、ENSへの固執を避け、比較文書の切り替え条件で判断する。
