# ENSかInterceptaか — 実装ゼロから受賞を狙う比較

確認日：2026-09-25

**追補：公式資料によるv1/v2比較を反映。取消だけではv2の差分が弱いため、ENSの検証対象を「エージェントへの限定委任と、権限外の書込拒否」に変更した。詳しくは[ENSv2の公式の推しどころ](ENSV2-DIFFERENTIATION.md)。**

**推奨：ENSを第一候補にし、時間を区切った技術検証で採否を決める。Interceptaは、実際に動く決済検査を用意できる場合の代替候補とする。**

これは比較と判断手順の提案であり、採用の最終決定ではない。ENSが受賞しやすいという実証データはない。応募数、競合作品、審査員の評価は不明なため、勝率や期待賞金を数字で作らない。

## 1. 判断の前提

- 目的は、製品の理想形より**今回の受賞を優先すること**。
- ユーザー確認では、ENS・Intercepta・World・x402・MultiBaasを含め、**まだ一つも実装していない**。
- 公開リポジトリにも実装コードはなく、設計・調査文書のみ。
- 既存戦略はCurvegridとWorldを優先し、3枠目をENS／Interceptaで比較している。
- チームの残り作業時間、APIキー・ウォレット・テスト資金の準備状況は未確認。
- 本書は公式賞ページを確認した比較。SDKの疎通、コントラクト呼び出し、API実測は未実施。

**いま一番避けたいのは、3社の説明はできるが、どの実装も完成しない状態。** 3枠目の選定で本体・決済・本人確認の完成を遅らせない。

ENSは賞金・受賞枠が多いが、それだけで勝ちやすいとは言えない。InterceptaもAPIがあるから短時間で完成するとは限らない。**比較すべきは、審査に出せる一周までの不確実性。**

## 3. ENSを第一候補にする理由

### 3-1. 一つの実装を、製品説明とスポンサー説明の両方に使える

Norenの中心は、依頼を `auto` / `human` / `deny` に分けること。ENS上の許諾を判断根拠にすれば、「どの状態を見て通したか」「なぜ次から止まるか」を同じデモで説明できる。

Interceptaは支払元のリスクに効くが、「この情報を、この用途で売ってよいか」は別に実装する必要がある。**ENSには中心機能への実装投資を、そのまま賞のデモにできる可能性がある。**

### 3-2. 今回のENS賞が求める使い方に寄せられる

公式賞ページは階層レジストリ、Enhanced Access Control、期限・取消などを紹介し、エージェントを名前空間として扱う応用も歓迎している。ただし、すべてを実装することが必須とは書かれていない。[S1]

**取消だけは従来版でも可能だった。** 今回はEAC＋Permissioned Resolverで、代理エージェントに提案レコードだけの更新を許し、本人の許諾・受取先は変更できない境界を実演する。限定委任を後付けにせず、ENSv2を検証する主題にする。根拠とリゾルバの権限スコープは[追加調査](ENSV2-DIFFERENTIATION.md)を参照。

### 3-3. 決済が未完成でも、許諾の技術検証を先にできる

ENS賞の正式要件に決済は含まれない。[S1] したがって、許諾の発行・参照・取消は決済実装から切り離して検証できる。

一方、Interceptaの対象賞には動くエージェント決済が必要。[S2] 現在は決済もゼロなので、「API一回を足すだけ」の状態ではない。

ただし、Noren全体とCurvegrid向けのデモでは決済が引き続き重要。ENSだけ動かして全体が完成したと判断しない。

## 4. ENSを過大評価しないための条件

- **ENSはルーティングや人間キューを作ってくれない。** 束ね方、優先順位、承認、期限処理はNoren自身の仕事。
- **許諾管理はDBや自前コントラクトでも実装できる。** 「ENSでしかできない」は主張しない。
- **名前の階層と、アプリの業務権限は自動で一致しない。** 名前を取り消した後にNorenが参照し、実際に情報提供・決済を止める必要がある。
- **親の取消が子の全処理を自動停止するとは未検証で断定しない。** 委任・独立性・参照方法を含め、選んだ構成で確認する。
- **公開レコードに個人情報の本文を置かない。** 何を公開するかは最小化し、許諾情報自体の公開範囲にも注意する。
- **書込成功だけでは不足。** アプリからの読取り、状態反映、取消後の拒否まで通す。

「なぜENSか」への回答案は、**許諾をNoren内だけの設定にせず、別のエージェントやサービスも参照できる共有の状態にするため**。外部からの読取りを実際に示せないなら、主張は弱くなる。

## 5. Interceptaを選ぶ方がよい条件

Interceptaの受取側検査は公式要件に明記されており、Norenへの適合はこじつけではない。[S2] 詳細は[INTERCEPTA.md](INTERCEPTA.md)を参照。

次の条件が揃えば、ENSよりInterceptaを優先する合理性がある。

1. APIキーがあり、実際のレスポンスと理由を確認できている。
2. 通過と停止のデモに使えるアドレス・検証方法が確保できている。
3. エージェント決済の一周が動き、署名前または受取前に検査を入れられる。
4. ENSの技術検証が時間内に通らず、本体の開発を圧迫している。

**現在は、この条件が揃っているとは確認できていない。** 「ENSで詰まったら確実にInterceptaで取れる」という保険にはしない。

### Intercepta特有の難所

- テストネット決済でも、mainnetの実在アドレスを検査する必要がある。モック・固定応答では資格を満たさない。[S2]
- 受取側なら、検査する支払元と実際の支払い認可を結びつける必要がある。
- 公開された危険アドレスの秘密鍵を持っている前提にはできない。無関係なアドレスを差し込んだ検査で「この支払いを止めた」と見せない。
- 受取側の検査で止める場合は、買い手の署名後になり得る。「署名前」ではなく「サービスの受取・決済前」と説明する。
- 外部APIが落ちたときの保留、理由表示、期限切れなども実装対象になる。

買い手側で危険な宛先を署名前に検査する構成は代替案になり得る。ただし、Norenが売り手側のルーターであることと、買い手デモの役割を区別して説明する。

## 6. 最小デモの比較

| | ENSを選ぶ場合 | Interceptaを選ぶ場合 |
|---|---|---|
| 最初の状態 | Aliceが許諾を設定し、代理に提案キーだけ委任 | 許諾条件を満たす買い手の依頼 |
| 通る場面 | 代理の提案更新が成功。Norenが本人の許諾と照合して処理 | live検査が通り、決済が成功する |
| 止まる場面 | 代理の許諾・受取先改変が拒否。委任取消後は提案更新も拒否 | 別の取引がlive検査で拒否・保留され、決済されない |
| 審査員に見せる根拠 | EACの権限・署名主体・書込成功／拒否・Norenの処理 | 検査対象・live結果・理由・処理分岐・決済結果 |
| 追加すると強いもの | 別クライアントから同じ許諾状態を読める | 許諾は有効でも受取だけを止めることが分かる |

最初から52件を実トランザクションで流す必要はない。まず、少数の依頼で**通る・人間に聞く・止まる**が本当に動くことを優先する。大量表示や将来の学習グラフは、その後。

## 7. 推奨する意思決定手順

時間は作業予測ではなく、**際限なく調査しないための提案上の上限**。残り時間が短ければ縮める。

### A. 最初の30分：アクセス条件だけ確認

- ENS：公式の現行デプロイ・必要な権限・テスト資金・親名の用意方法を確認する。
- Intercepta：キーの有無、利用可能なAPI、正当な通過／停止デモの作り方を確認する。
- スポンサーへの確認は、「面白いですか」ではなく「この最小デモを動かすための方法・リソースを教えてほしい」とする。

この文書作成では、キー申請やスポンサーへの連絡は行っていない。

### B. 次の90分以内：ENSだけを技術検証

完了条件は次の一周。

1. ENSv2上で本人の許諾を設定し、代理アカウントに提案キーだけの更新権限を付与できる。
2. 代理の提案更新は成功し、同じ代理の許諾キー・受取先の更新はコントラクトで拒否される。
3. 本人が委任を取り消すと、代理の提案更新も拒否される。
4. Norenが本人の許諾を読み、代理の提案だけでは処理を通さないことを確認する。

本人と代理の2アカウントに限定する。UI、装飾、52件処理、複雑な階層、多数のエージェントへの委任はこの検証に入れない。Resolverのキー権限は同じインスタンスの全名に及ぶため、分離範囲を確認する。

### C. 結果で選ぶ

| 検証結果 | 推奨 |
|---|---|
| ENSの一周が通る | **ENSを採用候補として確定し、本体へ接続** |
| ENSが通らず、Interceptaのキー・デモ条件が揃う | **Interceptaへ切り替え、決済の一周に集中** |
| ENSが通らず、Interceptaも条件未確保 | **3枠目の作業を止め、本命のデモを完成させる** |
| 両方とも成立しそう | **ENSを優先。両方の本実装に広げない** |

これは技術検証の提案であり、この文書作成をもって検証を開始したという意味ではない。

## 8. 前の資料から見直す点

| 前の説明 | 今回の整理 |
|---|---|
| InterceptaはNorenにぴったり | **賞の対象として適合するが、中心価値への寄与は追加的** |
| ENSの方が製品に近いから採用すべき | **相性だけでは不足。時間内に実動を示せる場合に採用する** |
| ENSの階層で一括取消が自動成立する | **選んだ構成とNorenの実行経路で確認が必要** |
| 取消の実演だけでENSv2の特徴を示せる | **取消自体は従来版にもある。限定委任と権限外書込の拒否を主題にする** |
| InterceptaはAPI一回なので簡単 | **キー・検査対象・決済フロー・停止の証明までが必要** |
| 賞金が多い方を選べば受賞に有利 | **競争状況は不明。賞金額と受賞確率は別** |

既存READMEのENS表記は現在の構想を示しているが、実装済みではない。本書も最終決定の記録ではないため、採否が決まった時点でREADME・CONCEPTの技術前提を揃える。

## 9. 提案の要点

**現時点の第一候補はENS。ただし「取消可能」ではなく、「代理エージェントは提案できても本人の許諾を書き換えられない」というEACの権限境界を、本体へ接続できることが条件。決済が未完成でも先に検証できる。**

ただし、受賞優先ならENSに固執しない。時間を区切って一周を確かめ、成立しない場合は準備の整ったInterceptaへ切り替える。両方が未成立なら、3枠目を埋めることより、動く製品を提出することを優先する。
